The Crawl-to-Rank Model

Technical SEO follows Google's own model of how a page reaches the results page: crawling, rendering, indexing, then ranking. A page has to be discovered before it can be understood, understood before it can be indexed, and indexed before it has any chance of ranking at all. Most technical SEO problems fail somewhere in the first three stages, which is why a page can look fine to a visitor and still be invisible in search — the visitor sees the rendered result, not the crawl and indexing process that happened before it.

Diagnosing a technical issue means working out which stage is actually broken. A slow site can still get crawled but waste crawl budget on low-value URLs. A JavaScript-heavy site can render correctly for a user but fail to render the same way for a crawler. A duplicate-content problem can get everything crawled and indexed, but split ranking signals across multiple near-identical URLs instead of consolidating them onto one.

Common Technical Issues I Look For

Crawlability and indexability. Whether important pages are actually reachable through internal links, whether robots.txt is accidentally blocking something valuable, and whether pages that should not be indexed are leaking into search results.

XML sitemap and robots.txt review. Whether the sitemap reflects the site's real, current structure, and whether robots.txt directives match what the business actually wants crawled.

Canonical tags and duplicate URL control. Whether parameterized URLs, filtered category pages, or HTTP/HTTPS and www/non-www variants are creating duplicate content that dilutes ranking signals instead of consolidating them.

Internal linking and site architecture. Whether the site's most important pages are close to the homepage in click depth, and whether internal links use descriptive anchor text instead of generic "click here" phrasing.

Core Web Vitals and performance signals. Loading speed, interactivity and visual stability, measured against Google's published thresholds rather than a vague sense that "the site feels slow."

Structured data and schema markup. Whether JSON-LD is present, valid, and actually matches the visible content on the page — mismatched schema can do more harm than no schema at all.

HTTP status codes, redirects and broken links. Redirect chains, soft 404s, and broken internal links that waste crawl budget and create a poor experience for both users and search engines.

Mobile usability and rendering. Since Google primarily uses mobile-first indexing, how the site renders on mobile devices is usually more important to ranking than how it renders on desktop.

How I Prioritize Technical Fixes

Not every technical issue deserves the same urgency. A canonical tag pointing to the wrong URL on a low-traffic page matters less than a robots.txt rule accidentally blocking the entire site. I rank findings by how directly they affect crawlability and indexing of important pages first, then by how much they affect user experience and Core Web Vitals, then by lower-impact cleanup items. That way a client with limited developer time knows exactly which three or four fixes to ship first instead of facing a fifty-item list with no clear starting point.

What a Technical SEO Audit Delivers

The output is a prioritized list of findings, each explained in plain language: what the issue is, why it matters for crawling, indexing or ranking, the evidence behind the finding — usually pulled from Search Console, crawl data, or direct inspection of the page — and a clear recommended fix. I try to write these so a developer with limited SEO background can act on them without needing a follow-up explanation for every item.

Working With Your Developer or Platform

Technical SEO fixes are only useful if someone can actually implement them. I take the platform into account — WordPress, Shopify, Webflow, a custom-built site — because the same underlying issue (say, a missing canonical tag) has a completely different implementation path depending on the CMS. Where possible, I provide fixes in a format your developer or platform's admin panel can use directly, rather than generic advice that still needs to be translated into a real implementation step.

Technical SEO tends to matter most for sites with either scale (large product catalogs, many templates, multiple subdomains) or complexity (JavaScript-heavy frameworks, multi-region setups, recent migrations). A small five-page brochure site usually has a shorter technical checklist than a thousand-product e-commerce catalog, and the audit scope should reflect that rather than applying the same depth of review regardless of site size.

Technical SEO Claims I Don't Repeat

Technical SEO has its share of outdated folklore: that a specific "SEO score" from a browser extension determines rankings, that keyword density has a precise ideal percentage, or that submitting a sitemap guarantees indexing. None of these are accurate representations of Google's actual documented guidance. Where a recommendation comes from confirmed Google documentation, I say so; where it is a reasonable industry practice without an official source, I label it that way instead of presenting it as settled fact.

How Long Technical SEO Takes to Show Results

Technical fixes do not move rankings overnight. A crawlability fix might get a blocked page indexed within days, but the ranking impact of that page depends on relevance, competition and content quality — factors technical SEO does not control on its own. Realistic timelines: indexing changes often show up in Search Console within one to a few weeks; ranking and traffic effects from a technical fix usually take longer to stabilize, especially on a site with low existing authority. I would rather set that expectation clearly upfront than let a client judge a correct technical fix against an unrealistic two-week timeline.

What a Realistic Engagement Looks Like

A typical technical SEO engagement starts with access: Search Console, analytics, and either a crawl of the site or direct access to relevant sections of it. From there, I build the baseline — current indexing status, crawl behaviour, and a list of technical issues found across the site, not just the homepage. Many audits stop at the homepage and a handful of top pages, which misses category-level or template-level problems that affect hundreds of URLs at once.

Once the baseline exists, findings get grouped by root cause rather than by individual URL. A broken canonical tag on a shared template affects every page using that template, so fixing the template fixes the problem site-wide instead of one page at a time. That grouping is usually where the biggest efficiency gains come from — a handful of template-level fixes can resolve far more indexing issues than fixing individual pages one by one ever would.

Frequently Overlooked Technical Signals

Some issues rarely make it onto a generic checklist but still cause real damage. Pagination that generates thousands of thin, near-duplicate URLs on an e-commerce site. Faceted navigation and filters that create an explosion of crawlable-but-worthless URL combinations. Hreflang tags that are present but misconfigured, sending international traffic to the wrong language version, or worse, confusing Google about which page to rank in which market. Log file evidence that Googlebot is spending most of its crawl budget on low-value URLs instead of the pages that actually drive revenue. These are the kind of findings a surface-level audit tool tends to miss, because they require actually reading crawl data rather than running an automated scan and listing whatever it flags.

Common Questions About Technical SEO

Does a technical fix guarantee a ranking increase? No. It removes a barrier that was preventing the page from competing fairly. Whether it then ranks depends on relevance, content quality and competition, which technical SEO does not control alone.

How often should a technical SEO audit be repeated? For most sites, a full audit once or twice a year, with lighter monitoring in between, catches new issues before they compound — especially after a redesign, migration, or major CMS update.

Can technical SEO be done without developer access? Some of it — sitemap and robots.txt review, for example — can be handled directly. Most meaningful fixes eventually need implementation access, whether that's a CMS admin panel or a developer's help.
