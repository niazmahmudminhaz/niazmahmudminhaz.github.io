What hreflang is for

Hreflang helps Google understand relationships between localized versions of a page. Google documents HTML, HTTP headers and XML sitemaps as ways to communicate alternate versions.

It is most useful when the variants are real localized pages. A one-language, one-market site does not need hreflang merely because people abroad can access it.

Build a complete relationship

Each relevant page should identify itself and the other relevant variants. Language comes first, with an optional region code. Use x-default as a fallback where appropriate.

Broken alternate URLs, missing self-references and inconsistent sets can undermine the implementation.

Coordinate hreflang with canonicals

Hreflang describes alternate versions; canonicalization communicates a preferred representative among similar URLs. They should not contradict the intended localization.

Regional pages that are genuinely distinct can remain canonical to themselves while hreflang communicates their relationship.

Validate after major changes

Check representative pages for valid codes, self-reference, reciprocity, indexable destinations and coherent canonical signals.

Migrations and CMS template changes can break hreflang quietly, so validation belongs in ongoing maintenance.

Practical checklist

  • Use genuine localized versions
  • Include self-reference
  • Use valid language-region codes
  • Reference relevant alternates
  • Coordinate canonicals
  • Validate after migrations

Questions people usually ask

Can hreflang be in a sitemap?

Yes. Google documents HTML, HTTP headers and XML sitemaps as supported methods.

What is x-default?

It can identify a fallback URL for users whose language or region is not separately represented.

Is a country code required?

No. Language is required; region is optional.
